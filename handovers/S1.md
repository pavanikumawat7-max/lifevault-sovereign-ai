## 5. Known issues

Issue (RESOLVED): The build sandbox used for this session had no
outbound network access and none of fastapi/pydantic/uvicorn/langgraph/
pytest/npm packages installed, so `api/schemas.py`, `api/routes/*`,
`api/main.py`, `graph/*`, the corresponding pytest modules, and the React
UI were written and syntax-checked (`ast.parse`, esbuild) but never
actually executed there.
Blocks demo?: No -- resolved.
Workaround/resolution: `pip install -r requirements.txt` and
`cd ui && npm install` were run successfully on a real developer machine,
and `python run.py`, `python scripts/smoke.py`, and `pytest -q` all now
pass end-to-end as documented.

Issue (RESOLVED): Once `pytest -q` could actually import langgraph, it
surfaced two real bugs that ast-level syntax checking could not have
caught:
1. `ValueError: 'answer' is already being used as a state key` on
   `graph.add_node("answer", nodes.answer)` -- LangGraph doesn't allow a
   state key and a node to share a name, and `LifeVaultState.answer` and
   the `answer` node collided. Fixed by renaming the internal state field
   to `answer_text` (`graph/state.py`, `graph/nodes.py`); the node itself
   is still named `answer`, and `/api/chat`'s external `answer` field is
   untouched.
2. `KeyError: 'execution_result'` on the no-proposal path -- `policy_check`
   routes straight to `audit_and_memory` when there's no proposal, so
   `execute` (the only node that ever set `execution_result`) never ran,
   and the key was simply absent from the final state. Fixed by also
   initializing `execution_result: None` in `retrieve` (the entry point,
   guaranteed to run on every path); `execute` still overwrites it with a
   real result once a later session implements it.
Blocks demo?: No -- resolved; `pytest -q` now reports `46 passed`.
Workaround: n/a.
