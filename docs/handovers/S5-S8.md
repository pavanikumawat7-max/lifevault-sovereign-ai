## 3. S5 — Watcher and OCR (P1's session)

**Built**

- `worker/watcher.py`: `watchdog` over every approved, unpaused root.
  Debounced (2 s), waits for file size to be stable for 2 s, skips
  `.part`/`.crdownload`/`.tmp`, hidden files, video, executables and DOCX,
  and **never watches the vault** (LifeVault writes `.ics`/`.eml` there;
  indexing its own output would loop).
- Events: created/modified mark the root dirty and trigger a re-scan;
  deleted flags `missing=1` and **keeps** the document, chunks and facts;
  moved is handled as delete + create, as specified.
- `worker/ocr.py`: RapidOCR with grayscale + autocontrast preprocessing.
  OCR is a **fallback only** — a PDF page with ≥50 characters of embedded
  text is never OCR'd. An image yielding under 8 characters is stored as
  metadata only.
- `worker/parse.py`: `parse_document()` dispatches PDF vs image; per-page
  OCR fallback; `ParsedPage.ocr` records which pages came from OCR.
- `worker/scanner.py`: images are now a supported format.

**Design note.** The watcher re-scans the affected root rather than
ingesting single files itself. That reuses the scanner's existing
(path, size, mtime) prefilter, hashing, duplicate handling and chunk
supersession instead of duplicating ~100 lines of subtle upsert logic. The
prefilter means unchanged files are never re-hashed, so a re-scan of the
104-document corpus is about a second.

**Tested (live, not mocked)**

- Copied a PDF into the indexed folder → **searchable in 4 s** (criterion: under 30 s).
- Deleted it → flagged `missing` in 5 s, document/chunks/facts intact.
- `.part` file → ignored (counted in `stats.events_ignored`).
- Duplicate file → one hash, two locations, no re-processing.
- `order_email.png` → OCR'd and **ranks #1** for "Dell UltraSharp monitor
  order", which is text that exists only in the image.

## 4. S6 — Fact extraction (P2's session)

**Built**

- `worker/facts.py`: keyword doc-type classifier (warranty / invoice /
  other), regex + `dateparser` extractors, `store_facts`, query helpers.
- Warranty fields: `expiry_date`, `start_date`, `serial`, `product`,
  `contract`, `vendor`. Invoice: `invoice_no`, `date`, `total`, `currency`,
  `vendor`.
- Dates stored twice: `value` keeps the document's wording ("June 12, 2027")
  so citations read naturally, `norm_value` keeps ISO ("2027-06-12") so
  `expiring_within` is pure SQL.
- **Every fact quotes its source, and the quote is verified.** `store_facts`
  refuses any fact whose `source_quote` is not literally present in the
  chunk it claims to come from.
- **User corrections are permanent.** `user_corrected=1` makes a row immune
  to being overwritten by re-extraction.
- `graph/retrieve.py: retrieve_facts()` injects fact rows into the evidence
  for date/money questions only, so ordinary questions keep undiluted chunks.
- Extraction runs automatically at the end of ingesting each document.

**Results on the demo corpus:** 13 facts from exactly the 3 real documents,
0 from the 101 filler records. The Dell warranty expiry, purchase date,
service tag, product and vendor, the invoice number, date, total and
currency, and the expired warranty's date and contract number are all
correct.

**Two bugs found and fixed during the session**, both worth knowing about
because the patterns are easy to regress:

1. `Invoice date June 12` captured `invoice_no = "date"`. The pattern now
   requires a digit and rejects label words.
2. `documents.title` is often the *filename*, so `_guess_vendor` returned
   `"warranty.pdf"`. Extensions are stripped and separators split now.
3. Classification threshold raised to 2 keyword hits: filler prose that
   says "receipt" once was being classified as an invoice, which filled the
   facts table with 10 spurious vendor rows.

## 5. S7 — Actions, approval and memory (P3's own session)

**Built**

- `api/tools/`: exactly two tools.
  `create_reminder` writes a `reminders` row and an RFC 5545 `.ics`;
  `draft_email` writes an RFC 5322 `.eml` and **never sends** — there is no
  SMTP client in the module and a test asserts there never is one.
- `api/tools/_vault.py`: one place that enforces "writes stay inside the
  vault". Filenames are rebuilt from a slug, so a parameter lifted out of
  document text cannot contain `..`, an absolute path or a NUL byte and escape.
- `policy/policy.py`: real allow-list plus `check_proposal`, enforcing
  (1) deny-by-default tool allow-list, (2) Pydantic parameter validation,
  (3) paths inside the vault, (4) at least one document citation,
  (5) untrusted-value flagging for injection-shaped text — flagged, not
  blocked, because a human decides.
- `graph/propose.py`: deterministic proposals from S6 expiry facts, plus a
  structured-LLM path. Memory supplies defaults (the reminder lead time),
  never permissions.
- `graph/approval.py`: proposal storage, edit merging with re-validation,
  edit diffs, and the `human_approval` node.
- `graph/execute.py`: re-reads the proposal row and **refuses anything not
  `approved`**; re-checks policy immediately before the handler runs.
- `graph/audit_memory.py`: appends `chat_turn`, `action_proposed`,
  `action_decided`, `action_executed` and `action_policy_denied` rows, and
  upserts memory. **Stores no document text** — only hashes, paths and the
  short quote already surfaced as a citation.
- `api/routes/approvals.py`: `POST /api/approvals/{id}` with
  approve/edit/reject, plus an additive `GET /api/approvals` queue.
- `api/routes/memory.py`: real.

### How interrupt/resume survives a restart

This was flagged as the session's top technical risk, so here is the exact
mechanism. **LangGraph is pinned `>=0.2,<0.3` and the dynamic `interrupt()`
only exists in 0.2.30+.** Rather than bump a shared dependency mid-project,
the graph uses the static interrupt available in 0.2.x:
`compile(interrupt_before=["human_approval"])`.

1. `POST /api/chat` invokes the graph with `thread_id = conversation_id`.
2. It runs retrieve → answer → verify → propose → policy_check, then stops
   **before** `human_approval`. The proposal row is already written with that
   `thread_id`.
3. The process can now die. The checkpoint is in `data/lifevault.db` via
   `SqliteSaver`; the row records which thread to resume.
4. `POST /api/approvals/{id}` finds the thread, writes the decision with
   `update_state`, and invokes with `None` to continue through `execute` and
   `audit_and_memory`.

Nothing about the pending turn is held in memory, which is why step 4 works
in a brand-new process. **Verified for real**: a proposal created in one
Python process was approved and executed in a separate, freshly-started one,
and there is a test (`test_approval_survives_a_restart_by_resuming_from_the_database`).

There is also a documented fallback: if no resumable checkpoint exists, the
route executes and audits directly, so a checkpointing detail can never lose
a decision the user already made.

**All eight S7 acceptance checks pass via the API:**

| Check | Result |
|---|---|
| propose | reminder proposed, due 30 days before expiry |
| pause at approval | run stops before `human_approval`, proposal `pending` |
| approve → executes | `.ics` written, status `executed` |
| edit → executes edited | diff `{due_date: 2027-05-13 → 2027-05-01}`, file named for the new date |
| reject → does not execute | status `denied`, `reminders` table untouched |
| denied tool blocked | `delete_files` → deny at policy *and* at execute |
| audit hash chain verifies | `valid: true`, 19 rows |
| restart mid-approval | resumes and executes (above) |

Memory works as precedent too: editing a reminder to 90 days before expiry
made the *next* proposal default to 90 days — the "because you did this
before" chip.

## 9. Known issues

**Issue 1 — Q5 refuses a question it can answer.** Blocks demo? No.
*"On what date was the Dell XPS 15 purchased?"* returns `could not verify`
even though the warranty says "Purchase date: June 12, 2026". The safe
failure mode (a refusal, not a wrong answer), and it is the last of a
sequence where each prompt change moved which single question the 3B
declines. Not worth more prompt tuning; a larger model or a targeted
`start_date` fact lookup would fix it. **Workaround:** ask "when was it
bought" differently, or read it off the Expiry page, where the fact is
correct.

**Issue 2 — the demo-script phrasing still refuses.** Blocks demo? **Yes,
that one line.** *"My Dell screen is flickering. Am I still covered?"*
returns `could not verify`. Retrieval is fine and the model cites the right
chunks; it will not make the two-step inference from "flickering screen" to
"hardware warranty covers this". Confirmed by a control: *"Is my Dell XPS 15
still under warranty?"* answers correctly. **Use that phrasing in the demo**,
or *"When does my Dell laptop warranty expire?"*.

**Issue 3 — small models drift in output shape.** Blocks demo? No.
The model occasionally returns a nested object for the `answer` field
(`{"passport_number": "None"}`). That is now detected and refused rather
than stringified into a sentence no human wrote. If you change the answer
prompt, re-run the eval — this failure mode comes back easily.

**Issue 4 — `ui/node_modules` is committed, and it is a Windows build.**
Blocks demo? **Yes, on any non-Windows machine.** `@esbuild/win32-x64` and
`@rollup/rollup-win32-*` are in the repository, so Vite dies with
`Permission denied` on macOS/Linux. I reinstalled locally to run the UI but
did **not** commit that. The fix is one commit:

```bash
echo "node_modules/" >> .gitignore
git rm -r --cached ui/node_modules
git commit -m "chore: stop tracking ui/node_modules (platform-specific)"
```

**Issue 5 — tracked `.pyc` files dirty the tree on every test run.**
Blocks demo? No, but it makes `git status` noise. `__pycache__` is tracked
despite being in `.gitignore`. Same fix shape as Issue 4.

**Issue 6 — first call after Ollama starts can take ~60 s** and surfaces as
`could not verify`, because `llm.chat`'s timeout is 60 s. Warm the model
before demoing: `ollama run llama3.2 "ready"`.

**Issue 7 — only one pending proposal per conversation.** By design: the
approval interrupt is per-thread, so a second simultaneous pending action
would have nowhere to pause. Extra candidates are returned on
`proposal_candidates` and visible in the audit log.
