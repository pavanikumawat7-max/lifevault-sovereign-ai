## 2. What I built

**Feature:** hybrid retrieval, cited answers, grounding verification, and a
real `POST /api/chat`.

**Scope done:**

- `hybrid_search`: FTS5 BM25 top 20 + sqlite-vec KNN top 20, fused with
  RRF (`score = sum(1 / (60 + rank))`, k=60). Superseded chunks skipped.
  Duplicate content collapsed by `content_hash`, with every other known
  location attached, so a file in two folders is one citation with an
  "also found at" rather than two hits.
- `retrieve` node returns chunks carrying `content_hash`, `abs_path`,
  `page` and `locations` (plus `also_found_at`, `title`, and the RRF score
  and per-ranker ranks, which made the eval table debuggable).
- `answer` node: chunks numbered `C1..Cn`, each fenced and explicitly
  framed as **untrusted data** that is evidence to quote and never an
  instruction to follow. Model returns JSON `{answer, cited_chunk_ids,
  confidence}`. Citations the model invents (a label it was never shown)
  are dropped and reported as a grounding failure, not honoured.
- `verify_grounding`: every date and every double-quoted phrase in the
  answer must appear in a chunk the answer **cites** (not merely something
  retrieved). Dates are compared semantically, so `2027-06-12` passes
  against `June 12, 2027` but `June 12, 2028` does not. On failure the
  answer is regenerated once with the specific reason fed back; if it
  fails again the answer is replaced with the literal `could not verify`.
- `POST /api/chat` returns JSON, no streaming. It invokes the **compiled
  LangGraph** rather than calling the nodes directly, so S7 can fill in
  `propose_action` / `human_approval` without editing `chat.py` (which is
  not in S7's allowed file list).
- `scripts/eval.py`: 10 questions with expected answers *and* expected
  source files, per-answer latency, markdown + JSON output, model override
  for comparisons, and a warmup call excluded from timings.
- Latency measured and the model choice recorded in the README.

**Not done / cut:**

- No streaming, facts, proposals, tools or UI work -- all out of S3 scope.
- **The 7B latency comparison was not run** (no 7B model pulled on this
  machine, a ~4 GB download). `phi3` (3.8B) was measured instead as the
  larger-model data point: 50.1s median vs 7.8s for the 3B. The exact
  command to measure a 7B is in the README.

## 5. Known issues

**Issue 1: the 3B model sometimes refuses a question the retrieval
answered.** Blocks demo? **Not by itself, but it affects one demo line.**

Two reproducible cases:

- Eval Q9 (*"What is the reference number on the synthetic travel record
  003?"*): `record_003.pdf` is retrieved at **lexical rank 1** and its text
  contains `Reference DEMO-0003`, and the model still replies `could not
  verify`.
- The demo-checklist phrasing *"My Dell screen is flickering. Am I still
  covered?"*: retrieval puts `dell_warranty.pdf` in the top 4 and the model
  cites it, but will not assert that a flickering screen is covered --
  that needs an inference beyond the document text.

This is a model-capability limit, not a retrieval or code bug: in both
cases the right chunk is retrieved and cited. Deterministic now that the
answer temperature is pinned to 0.

Workaround / fix path, in the handover plan's own terms ("Local model
speed -> facts and dates from SQL"): **S6's fact extraction is the real
fix** -- with warranty expiry available as a structured fact row injected
into `retrieve`, the answer stops depending on the model inferring
coverage. Until then, the reliable demo phrasing is *"When does my Dell
laptop warranty expire?"*, which passes every run. A larger model would
also fix it but costs ~50s per answer on this laptop.

**Issue 2: vector retrieval adds noise on this corpus.** Blocks demo? No.
Workaround: none needed.

98 of the 103 demo documents are lorem-ipsum filler with near-identical
embeddings, so the semantic arm's top-20 contains unrelated records that
RRF then scores alongside genuine lexical hits. For well-formed questions
this is harmless (the relevant chunk still lands in the top 4, which is
all the answer prompt sees), but it is why the conversational phrasing
above ranks the warranty 3rd instead of 1st. Retrieval tuning is P2's
Day-5 B2 block; the per-ranker ranks and RRF score are exposed on every
retrieved chunk to make that work measurable.

**Issue 3: cold model load can look like a failure.** Blocks demo?
**Yes, if the model is cold.** Workaround: warm it first.

The first call after Ollama starts takes ~60s on the dev laptop, which is
at `llm.chat`'s 60s `requests` timeout. It surfaces as `could not verify`
rather than an obvious timeout. `scripts/eval.py` warms the model
automatically; a demo must do it manually. Raising that timeout is in
`llm.py`, which belongs to P1, so it is flagged rather than changed.

**Issue 4: fixture mode has no semantic signal.** Blocks demo? No.

`llm.embed` returns a zero vector in fixture mode, so every stored vector
is equidistant and only the BM25 arm ranks. This is expected -- fixture
mode exists to run with no model -- but it means fixture-mode retrieval
quality is not representative, and `scripts/eval.py`'s content checks only
pass against a real model.

**Issue 5: latency is machine-load sensitive.** Blocks demo? No.

Median per-answer latency measured 7.8s warm, but 13-18s on earlier runs
of the same questions on the same machine (8 GB is tight with both models
resident). Re-measure on the actual demo laptop rather than trusting this
number.
